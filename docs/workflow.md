# 記録の流儀: 課題 → 対策 → 結果 → 判断 を git に残す

チャットは消える。残すのはテキストで、置き場は決めておく。このリポジトリでは次の 5 か所だけを使う。
新しいプロジェクトを立ち上げるときは、この文書と `.github/`、`plans/`、`decisions/`、`prompts/` をそのままコピーして始める。

## 置き場

| 種類 | 置き場 | 1 件の単位 | 書く人 |
|---|---|---|---|
| 課題 | GitHub Issue(テンプレ: `.github/ISSUE_TEMPLATE/kadai.md`) | 困りごと 1 つ。「使っていて困った事実」から始める | 本人が気づく。Claude が issue 化してよい |
| 対策(計画) | `plans/YYYY-MM-DD-名前.md`(テンプレ: `plans/TEMPLATE.md`) | issue 1 つに対する作戦。やること・やらないこと・検証方法 | Claude が下書き、本人が「やらないこと」と「検証方法」を確認 |
| 実装 | ブランチ + PR(テンプレ: `.github/pull_request_template.md`) | 1 つの意図。PR 本文に `Closes #N` と検証結果 | Claude |
| 結果 | issue を閉じるコメント | 数字(使った記録)と事実。期待どおりか、違ったか | Claude が下書き、本人が判断 |
| 判断 | `decisions/NNNN-名前.md`(テンプレ: `decisions/README.md`) | 決めたこと 1 つ。文脈・決定・理由・捨てた案・根拠 | 本人の判断を Claude が記録 |

prompt は捨てない。`plans/` の文書は、そのまま Claude への指示として使う(plan = prompt)。繰り返し使う指示は `prompts/` に置く。

## 1 周の流れ

```
気づく ──▶ Issue(課題)
             │  「課題: 食事が 3 枠中 1 枠しか拾えない」
             ▼
          plans/(対策) ── やること / やらないこと / 検証方法 / 期限
             │
             ▼
          ブランチ → PR → CI 緑 → マージ(実装)
             │  PR 本文: 何を・なぜ・どう検証したか・指標の変化
             ▼
          Issue を閉じる(結果) ── 「2 週間で捕捉 7/21 → 15/21。手入力 9 → 3」
             │
             ▼
          decisions/(判断) ── 「決済通知だけでなくカレンダーの会食予定も食事の証拠にする」
```

小さい修正(誤字、1 行の直し)は issue も plan も要らない。PR は要る(main への直 push は `.githooks/pre-push` が止める。private + Free では GitHub の保護が使えないため)。
issue が要るのは「使っていて困った」「数字が悪い」「方針を変えるか迷う」のどれかに当たるとき。

## 書き方の約束

- **課題は事実から。** 「食事の推定が雑」ではなく「10/9〜10/15 の 7 日で、食事カードが出た枠は 21 中 13」。使った記録の数字をそのまま貼る。
- **対策には「やらないこと」を必ず書く。** 機能は足す前に消す。書けないなら作戦が大きすぎる。
- **結果は期待と比べる。** plan の「検証方法」に書いた数字と、実際の数字を並べる。期待どおりでなかった事実こそ残す。
- **判断は捨てた案も書く。** 1 年後の自分が「なぜこれを選ばなかった」を読めるように。
- **AI の文章は材料、判断は人。** plan の「やらないこと」、結果の「期待どおりか」、decision の「決定」は本人が書くか、本人が読んで承認する。

## 複数プロジェクトで使うとき

- プロジェクトごとにリポジトリを分け、この 5 か所を同じ名前で持つ。探す場所が同じなら、Claude も人も迷わない。
- プロジェクトをまたぐ判断(例: 無料枠のみ、API キーを持たない)は、各リポジトリの `decisions/` に「出典: hub#0001」や「出典: wellness-app#0002」の形で引用して持ち込む。コピーではなく参照にして、元を 1 つにする。
- `CLAUDE.md` の絶対ルールは、`decisions/` で決まったことの要約。decision を書いたら CLAUDE.md を見直す。

## Claude への指示の仕方(例)

skill: `/kadai <困った事実>`(issue 化)、`/kekka <番号>`(結果の下書き)、`/shuho`(週報の下書き)。文章で頼むなら:

- 「課題: ○○」→ issue を作る(テンプレに沿って、事実と数字を埋める)
- 「#3 の対策を考えて」→ `plans/` に下書きし、「やらないこと」と「検証方法」を確認してもらう
- 「#3 をやって」→ ブランチを切り、plan のとおり実装し、CI を通して PR を出す
- 「#3 の結果をまとめて」→ 使った記録の数字で結果コメントを下書きし、閉じるかを本人に聞く
- 「これは決定にして」→ `decisions/` に記録し、必要なら CLAUDE.md を更新する
